= Cluster Guide

== About this guide

This guide is for the local k3d cluster `ff-logistic`.
It covers the one setup that otherwise has to be repeated on every command: making `k3d-ff-logistic` the current kubectl context on both WSL and Windows.

The cluster is created from `deploy/cluster/k3d-config.yaml`.
k3d writes its kubeconfig into the Linux home (`~/.kube/config` in Ubuntu) and, because that file sets `switchCurrentContext: true`, WSL kubectl already points at `k3d-ff-logistic` after `k3d cluster create`.
Windows kubectl reads a different file, `C:\Users\<you>\.kube\config`, and does not see the WSL one.

[[current-context]]
== Current context

=== Windows kubectl still talks to another cluster

Symptom:: `kubectl config current-context` on Windows prints `microshift` (or `docker-desktop`). `kubectl get ns` fails against `https://127.0.0.1.nip.io:6443`. The same command in WSL lists `argocd`, `default`, `kube-system`.
Check:: `kubectl config get-contexts`. On Windows, `k3d-ff-logistic` is missing. In WSL it is present and marked current.
Cause:: k3d runs in WSL and updates only the WSL kubeconfig. IntelliJ can show `k3d-ff-logistic` as current because the IDE was pointed at `\\wsl.localhost\Ubuntu\home\<linux-user>\.kube\config`. That selection is the tool window's cluster, not Windows kubectl's current context. The checkbox that copies clusters into `C:\Users\<you>\.kube\config` does not always land; confirm with `kubectl config get-contexts` afterwards.

The command that selects a context is `kubectl config use-context`.
It only works when the name is already in the file it is reading.
`kubectl config set-context` edits a context's cluster and user; it does not switch, and it cannot invent the certificate data k3d generated.

Fix:: Copy the one context out of WSL, merge it into the Windows kubeconfig, then select it.
Keep the other contexts (`microshift`, `docker-desktop`). Take a copy of the Windows file first.

From PowerShell:

[source,powershell]
----
$kube = Join-Path $env:USERPROFILE '.kube'
$main = Join-Path $kube 'config'
$extra = Join-Path $kube 'k3d-ff-logistic.kubeconfig'
$merged = Join-Path $kube 'config.merged'

Copy-Item $main "$main.bak" -Force
wsl -e bash -lc "k3d kubeconfig get ff-logistic > /mnt/c/Users/$($env:USERNAME)/.kube/k3d-ff-logistic.kubeconfig"

cmd /c "set KUBECONFIG=$main;$extra&& kubectl config view --raw --flatten > $merged"
Get-Content $merged -TotalCount 1   # must be: apiVersion: v1

Move-Item $merged $main -Force
Remove-Item $extra -Force
kubectl config use-context k3d-ff-logistic
----

Write the flattened file with `cmd` redirection.
Assigning `kubectl config view` to a PowerShell variable and writing it back has produced a kubeconfig kubectl then refuses to load (`yaml: mapping values are not allowed in this context`).
If that happens, put `$main.bak` back over `$main` and run the block again.
Do not replace `config` until the merged file starts with `apiVersion: v1`.

In WSL, if the current context has drifted:

[source,bash]
----
kubectl config use-context k3d-ff-logistic
----

Check, with no `--context`, from both shells:

[source,bash]
----
kubectl config current-context    # k3d-ff-logistic
kubectl get ns                    # argocd, default, kube-system, ...
----

Repeat the merge after `k3d cluster delete ff-logistic` and a new `k3d cluster create`.
The API address in the exported kubeconfig is chosen by k3d and changes with the cluster.
To go back to a context that stayed in the file: `kubectl config use-context microshift`.

=== IntelliJ does not list the cluster

Point *Add Cluster* at the WSL kubeconfig, `\\wsl.localhost\Ubuntu\home\<linux-user>\.kube\config` (the `\\wsl$\Ubuntu\...` form is the same file).
Select `k3d-ff-logistic` only.
The Windows file above is what `kubectl` in a Windows terminal uses; the IDE can keep reading the WSL file directly.

[[argo-ui]]
== Opening the Argo CD UI

The UI is published on the host as `8080`, mapped to the `argocd-server` NodePort `30080`.
No port-forward.

Open `http://127.0.0.1:8080`.
`http://localhost:8080` fails on Windows with `ERR_EMPTY_RESPONSE`: `localhost` resolves to `::1` first, and k3d publishes the port on IPv4 only.

[[start]]
== Starting the cluster again

Windows stops WSL after a while without a terminal, and Docker Engine runs inside WSL: the cluster's containers stop with it.
Open a WSL terminal, then:

[source,bash]
----
docker ps                          # Docker answers; if not: sudo service docker start
k3d cluster list                   # ff-logistic 1/1, or 0/1 when it is stopped
k3d cluster start ff-logistic
kubectl get nodes                  # Ready
----

The pods come back on their own within a few minutes; some restart once while PostgreSQL starts.
Keep one k3d cluster running at a time: two clusters cannot both publish `8080`.

=== The load balancer does not get ready

Symptom:: `k3d cluster start` ends with `FATA … Node k3d-ff-logistic-serverlb failed to get ready`: k3d waited for the log line `start worker processes` and did not see it. kubectl says `The connection to the server 0.0.0.0:<port> was refused`. IntelliJ shows `Error while proxying request: dial tcp 0.0.0.0:<port>`.
Check:: Kubernetes itself, past the load balancer: `docker exec k3d-ff-logistic-server-0 kubectl get nodes` prints the node `Ready`. Then the load balancer's networks:
+
[source,bash]
----
docker inspect -f '{{.RestartCount}} restarts | networks: {{range $k,$v := .NetworkSettings.Networks}}{{$k}}={{$v.IPAddress}} {{end}}' k3d-ff-logistic-serverlb
----
+
It shows many restarts and no network after `networks:`. Its log ends with `creating initial nginx config (try 3/3)`.
Cause:: An earlier start failed while Docker connected the container to its network. Publishing the ports is part of that step; the usual reason is another k3d cluster holding `8080` (`Bind for 0.0.0.0:8080 failed: port is already allocated`). Docker undid the step and left the container with no network. Without one, nginx cannot find `k3d-ff-logistic-server-0`; it exits, and Docker starts it again. Every later `k3d cluster start` reuses that container.
Fix:: Stop whatever holds the port (`k3d cluster stop <other>`), then connect the load balancer to the cluster's network again:
+
[source,bash]
----
docker stop k3d-ff-logistic-serverlb
docker network connect k3d-ff-logistic k3d-ff-logistic-serverlb
docker start k3d-ff-logistic-serverlb
kubectl get nodes                  # Ready
----
+
Seen on 2026-11-20, after a break with the `lf` lab cluster also set to start with Docker. Nothing in the cluster was lost: k3s and the pods ran the whole time, behind a closed door.

[[sessions]]
== Sessions that expire

Two logins end on their own, and both look like something else when they do:

[cols="2,1,3,3",options="header"]
|===
| Session | Lasts | What it looks like when it ends | Renew

| The API token from `localhost:8085/sessions`, used by `curl` with `${H[@]}`
| minutes
| A request answers `401` with an empty body: `curl -s … \| jq` prints nothing at all, or `null`.
| Take a new token (the same `TOKEN=$(curl …)` line). Print `+%{http_code}+` when an answer looks empty.

| The `argocd` CLI's session
| 24 hours
| `argocd app sync` fails with `rpc error: code = Unauthenticated … token is expired`; nothing is synced, and whatever the sync would have brought (a migration, a new schema) is missing.
| `argocd relogin`, and the password at the prompt. Typed at the prompt, it stays out of the shell's history.
|===

Shell variables live in one terminal too: a value set in one (`TOKEN`, `H`, a request body) is empty in the next. In a new terminal, set them again first.

[[load]]
== A load test

`deploy/load/run.sh` runs the walkthrough as a k6 scenario (`deploy/load/walkthrough.js`) against the edge, as a Job in the cluster, and samples the pods' CPU and memory with `kubectl top` every 15 seconds while it runs. The edge answers with whichever side is active, so the same command measures either side.

[source,bash]
----
deploy/load/run.sh            # 10 virtual users: 30 s warm-up, 3 minutes measured
deploy/load/run.sh 20 5m 60   # 20 users, 60 s warm-up, 5 minutes measured
----

It prints, and saves as `load-<side>-<time>.txt` where it was started:

* the side's pods at rest;
* per request (`plan`, `shipment`, `pickup`, `departure`, `deliver`, `warehouses`, `distance`, and `sign-in`): the count, the failures, the median, p95, p99 and the slowest;
* each pod's highest CPU and memory under load, for the side and for the platform both sides share (PostgreSQL, Kafka, identity, the analytics loader).

The users first run 30 seconds unmeasured: the first requests after a quiet spell meet cold code (the JVM compiles as it goes, connection pools fill up), and neither side should be judged on that. Only the measured phase is counted, and only then are the pods sampled.

Every iteration plans a shipment, delivers it to the Hadimkoy hub and so opens an arrival there: the data grows with each run. Lists that grow (shipments, arrivals) are not read, so a later run is not slower for it. The Job and its pod stay a day, for `kubectl logs`.
